# Самостоятельная практика: две новые витрины

В видео разобрана `marts.mart_sales_daily`. Теперь расширь тот же DWH: добавь свои модели, проверки и выполни их через существующий DAG `academy_dwh`.

Все данные уже есть в Postgres, в схеме `academy`. Airflow переносит все восемь таблиц в `raw` Greenplum. Дополнительные CSV, API и генераторы для заданий не нужны.

## Перед началом

1. Запусти стенд по [README](../README.md) и дождись успешного DAG.
2. Посмотри готовые модели в `dbt_project/models/staging`, `core` и `marts`.
3. Создавай SQL-модели в соответствующих каталогах, зависимости задавай через `source()` и `ref()`.
4. Описания и проверки добавляй в YAML рядом с моделями либо в `models/schema.yml`. Бизнес-проверки можно добавить в `dbt_project/tests`.

Папки уже настроены на схемы Greenplum: staging-модели будут представлениями, core и marts — таблицами. DAG выбирает модели по папкам, поэтому новые модели попадут в следующий запуск автоматически. Его завершающая проверка продолжит проверять готовую витрину продаж; проверки своих моделей нужно написать самому.

Пользуйся готовым финансовым правилом: `net_kopecks` — оплаченная стоимость после скидок и обработанных возвратов. Все деньги в core заданы в копейках, в витринах — в рублях. Описание данных и связей — в [гайде](DWH_GUIDE.md).

## Задание 1. Накопленные покупки студентов

**Сложность: medium.**

### Контекст и цель

Маркетолог хочет увидеть, кто покупает курсы повторно, сколько уже потратил каждый студент и из какого канала он пришёл. Создай `marts.mart_student_ltv`.

### Дано

| Готовая модель | Нужные данные |
|---|---|
| `core.dim_students` | `student_id`, имя, email, текущий город, `acquired_via` |
| `core.fct_orders` | Заказ, студент, дата заказа, `is_paid`, `net_kopecks` |

### Требования

Одна строка — **один студент**, включая тех, кто ничего не оплатил.

| Поле | Значение |
|---|---|
| `student_id` | Ключ студента |
| `full_name`, `email`, `city`, `acquired_via` | Текущие атрибуты из измерения |
| `paid_orders` | Число оплаченных заказов |
| `observed_ltv_rub` | Сумма покупок после возвратов за загруженную историю, в рублях |
| `first_purchase_date`, `last_purchase_date` | Первая и последняя даты оплаченных заказов |

- Для студента без оплат количество заказов и сумма равны нулю, даты покупок — `NULL`.
- Отменённые и неоплаченные заказы не считаются покупками.
- Один заказ с двумя курсами считается одной покупкой.
- Используй текущий город студента: исторический город на дату покупки в этом задании не восстанавливается.
- `observed_ltv_rub` показывает уже совершённые покупки за имеющуюся историю. Прогноз будущих трат не требуется.

### Самопроверка и критерии приёмки

- На исходном наборе в витрине 200 строк; ключ не пустой и уникальный.
- Сумма `paid_orders` совпадает с числом оплаченных заказов в готовом core.
- Сумма `observed_ltv_rub` совпадает с суммой `net_sales_rub` в готовой витрине продаж.
- Студенты без покупок присутствуют с нулевыми показателями.
- После применения `scripts/demo_changes.sql` и запуска DAG у студента №1 появляются новая покупка и обновлённый город.
- Повторный запуск DAG не меняет количества и суммы при неизменном источнике.
- Добавлены dbt-проверки ключа, связи со студентами и сверки денег. Все проверки проходят.

<details>
<summary>Подсказки</summary>

- Сначала определи, на какой стороне соединения должен находиться полный список студентов.
- Проверь детализацию финансового источника: факт заказов и факт позиций дают разное количество строк.
- Условия в `WHERE` после внешнего соединения могут убрать студентов без покупок.
- Для денег и количества отсутствие покупок означает ноль. Для даты покупки разумнее сохранить отсутствие значения.

</details>

## Задание 2. Продажи курсов и прогресс обучения

**Сложность: hard.**

### Контекст и цель

Продюсер онлайн-школы хочет сравнивать продажи с тем, как студенты проходят курсы. Создай `marts.mart_course_performance`. Данные обучения проведи через собственные staging- и core-модели.

### Дано

| Источник или готовая модель | Что внутри |
|---|---|
| `raw.enrollments` | Зачисление на купленную позицию: `enrollment_id`, `order_item_id`, `enrolled_at` |
| `raw.lesson_events` | Доставки событий: `delivery_id`, `event_id`, зачисление, номер урока, тип события, время события и получения |
| `core.fct_order_items` | Позиция, студент, курс, признак оплаты и суммы |
| `core.dim_courses` | Курс, название, категория и `total_lessons` |

В исходном наборе есть повторные доставки одного события и зачисления без событий. В типах событий встречаются пробелы и разный регистр. Цены и количество уроков различаются между курсами.

### Что нужно построить

| Модель | Детализация и назначение |
|---|---|
| `staging.stg_enrollments` | Одна строка на зачисление, нужные поля источника |
| `staging.stg_lesson_events` | Одна строка на логическое событие после очистки и устранения повторных доставок |
| `core.fct_learning_progress` | Одна строка на зачисление, включая нулевой прогресс |
| `marts.mart_course_performance` | Одна строка на курс: финансовые показатели и обучение |

### Правила обработки событий

- `delivery_id` — идентификатор доставки сообщения, `event_id` — идентификатор логического события.
- При нескольких доставках одного события используй последнюю по `received_at`. При равенстве времени выбери доставку с наибольшим `delivery_id`.
- Нормализуй тип события; для прогресса учитывай только `lesson_completed`.
- Число завершённых уроков считай по уникальным номерам уроков внутри зачисления. Два разных события об одном уроке не означают два завершённых урока.
- Допустимый номер урока — от 1 до `total_lessons` соответствующего курса. Нарушение должно обнаруживаться проверкой.

### Требования к факту прогресса

В `fct_learning_progress` нужны ключи зачисления, позиции, студента и курса, дата зачисления, количество всех и завершённых уроков, `progress_pct`, `is_completed` и `last_activity_at`.

- Процент прогресса = завершённые уроки / все уроки × 100; округление до двух знаков.
- Зачисление завершено, если пройдены все уроки курса.
- Последняя активность определяется по `event_at` учитываемых событий.
- Зачисление без событий должно остаться с нулевым прогрессом, `is_completed = false` и `last_activity_at = NULL`.
- Зачисление является единицей обучения. Повторные покупки одного курса одним студентом могут создавать разные зачисления.
- В этом задании возврат денег сам по себе не удаляет зачисление и не сбрасывает прогресс.

### Требования к витрине курсов

| Поле | Значение |
|---|---|
| `course_id`, `course_title`, `category` | Курс и его текущие атрибуты |
| `sold_items` | Число оплаченных позиций курса |
| `buyers` | Число уникальных студентов с оплаченной позицией курса |
| `net_sales_rub` | Продажи после скидок и обработанных возвратов |
| `enrollments` | Число зачислений на курс |
| `completed_enrollments` | Число полностью завершённых зачислений |
| `completion_rate_pct` | Доля завершённых зачислений в процентах |
| `avg_progress_pct` | Среднее значение `progress_pct` по всем зачислениям курса, включая нулевой прогресс |

Сохрани все курсы, в том числе курсы без продаж или зачислений. Отсутствующие количества и деньги равны нулю. Если зачислений нет, `completion_rate_pct` и `avg_progress_pct` равны `NULL`: оценить обучение пока нельзя. Проценты округляй до двух знаков.

### Самопроверка и критерии приёмки

- На исходном наборе 4 223 доставки дают 3 700 логических событий. Факт прогресса содержит 640 зачислений, витрина — 6 курсов.
- Ключ каждой модели не пустой и уникальный; ссылки на родительские сущности проверяются.
- Количество завершённых уроков не превышает количество уроков курса; прогресс лежит от 0 до 100.
- Зачисления без событий сохраняются и входят в знаменатель показателей обучения.
- Сумма продаж по курсам совпадает с готовой витриной продаж. Количество событий не должно влиять на финансовые суммы.
- После `demo_changes.sql` добавляются два зачисления и две доставки одного события. После обработки должны появиться одно новое логическое событие и один завершённый урок для зачисления №10011; второе новое зачисление остаётся с нулевым прогрессом.
- Повторное применение демонстрационного SQL и повторный запуск DAG не меняют результат.
- Добавлены проверки диапазонов, связей и финансовой сверки. Общий `dbt test` проходит.

<details>
<summary>Подсказки</summary>

- Раздели логическое событие и доставку. Первичный ключ исходной таблицы отражает только доставку.
- Для выбора одной доставки обдумай оконную функцию с устойчивым порядком.
- Перед каждым JOIN запиши, что означает одна строка с каждой стороны. Проверь, сколько совпадений может найти строка.
- Продажи и события имеют разную детализацию. Финансовая сумма не должна повторяться на каждом уроке.
- Для курсов без зачислений предусмотрено отдельное поведение: деление на ноль здесь не подходит.

</details>

## Как проверить и сдать работу

Запусти DAG через интерфейс Airflow или командой:

```bash
docker compose exec -T airflow-scheduler airflow dags trigger academy_dwh
```

Дождись его завершения. Добавленные модели должны появиться в нужных схемах, а задача `dbt_test_all` — проверить весь проект. Для проверки моделей без повторного извлечения данных, когда DAG не выполняется:

```bash
docker compose exec -T airflow-scheduler /opt/dbt-venv/bin/dbt build --project-dir /dbt --profiles-dir /dbt
```

К работе приложи:

- SQL-модели и dbt-проверки;
- короткое описание детализации каждой новой модели;
- результаты самопроверки до и после `demo_changes.sql`;
- пояснение, как ты сохранил строки без покупок/событий и избежал размножения финансовых сумм;
- подтверждение, что повторный запуск даёт тот же результат.
